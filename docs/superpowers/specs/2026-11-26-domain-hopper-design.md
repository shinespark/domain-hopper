# domain-hopper 設計

## 目的と背景

今開いているページを、パス・クエリ・ハッシュはそのままで、同じプロジェクトの別の環境（本番・本番アドミン・ステージング・ローカルなど）へ切り替える Chrome 拡張を作り、Chrome Web Store に公開する。

Chrome Web Store には Domain Switcher などの似た拡張が多数あるが、次の点が不満で作り直す。

- UI の作りが粗い。ポップアップのボタンから文字がはみ出すなど、UI/UX として満足できる水準になっていない
- 作者や出どころが分からない拡張があり、閲覧中のページの URL に触れる拡張としてセキュリティ面で信頼しきれない
- 登録の仕組みがスマートでない

差を出すのは機能の多さではなく、「崩れない UI」「信頼できること」「最小の手数での登録と切り替え」の 3 点。

## ゴール

- 拡張のボタンを押すと、今いるページが属するプロジェクトの行き先一覧が出て、1 クリックで切り替えられる
- 今いるページから 1〜2 手で、新しいプロジェクトの作成、既存のプロジェクトへの追加ができる
- `https://` と `http://`、ポート番号付き（例: `http://localhost:3000`）の行き先を区別して扱える
- 1 つのプロジェクトに 4 つ以上の行き先（ステージングが複数ある、アドミン用ドメインがあるなど）を登録できる
- 登録内容が、同じ Google アカウントでログインしている自分の Chrome 同士で同期される
- 英語と日本語に対応する。Chrome の表示言語で自動的に切り替わる
- Chrome Web Store に公開する

## ゴールにしないこと

- 今のドメインから仲間の環境を推測して候補を出す機能（自動提案はいらないとユーザーが判断済み）
- URL を複数行まとめて貼り付けて一括登録する機能（ユーザーが不要と判断済み）
- 書き出し・読み込みや、チームメンバーへの設定の配布
- 切り替え先でのログイン状態や Cookie の引き継ぎ
- ポップアップから、今のページが属さないプロジェクトの行き先へ飛ぶこと

## 失敗とみなすこと（動いていても NG）

- 長いドメインやラベルでレイアウトが崩れる、文字がはみ出す
- `<all_urls>` などの広いホスト権限や `tabs` 権限を要求する
- 外部への通信（解析、エラー送信、リモート設定の取得など）を行う
- 1 回の切り替えに、ボタンを押してから 2 クリック以上かかる

## 制約

- Chrome 拡張 Manifest V3
- 権限は `activeTab` と `storage` のみ。ホスト権限は要求しない
  - ポップアップを開いた時点で `activeTab` により今のタブの URL が読める。タブの URL の書き換え（`chrome.tabs.update`）と新しいタブの作成（`chrome.tabs.create`）は権限なしで呼べる
- 外部への通信を一切行わない。フォントやアイコンもパッケージに同梱する
- 保存先は `chrome.storage.sync`。上限は全体で約 100KB、1 項目あたり約 8KB、項目数 512
- リポジトリ shinespark/domain-hopper は public。main への force push と削除はルールセットで禁止されている

## 作り方の検討

| 案 | 内容 | 引き換え |
|---|---|---|
| **WXT ＋ TypeScript ＋ React（採用）** | Chrome 拡張用フレームワーク WXT（Vite ベース）で manifest 生成・`_locales`・ホットリロード・ストア提出用 zip をまかなう。UI は React | 開発用の依存は増える（配布物には入らない） |
| Vite ＋ TypeScript、UI フレームワークなし | manifest と zip 作成を自前で書き、UI は素の DOM 操作 | インライン編集や並べ替えなど状態が変わる UI を手で組むと崩れやすく、「UI がちゃんとしている」という一番の目的に手間がかかる |
| ビルドなしの素の JavaScript | manifest と HTML/JS をそのまま置く | 型チェックもテストの土台もなく、「今の技術で作る」という希望から外れる |

UI ライブラリは当初 Svelte を推したが、ユーザーから「あまり使われていない」と指摘があり React に変更した。ポップアップは PC 内のファイルから読み込まれるので、React のランタイム（40〜50KB 程度）による速度差は体感できない。読める人が多く、公開リポジトリとして第三者がコードを確認しやすい利点を取る。

## 設計

### データモデル

- **プロジェクト**: `id`、`name`、行き先の配列（並び順を持つ）
- **行き先（環境）**: `id`、`label`、`origin`
  - `origin` は `スキーム://ホスト[:ポート]` の形（例: `https://stg1.example.com`、`http://localhost:3000`）。URL の `origin` と同じ正規化をする（デフォルトポートは省く、ホストは小文字）
- 1 つの `origin` は 1 つのプロジェクトにしか属さない。すでにどこかに登録済みの `origin` は追加できず、どのプロジェクトに入っているかを表示する
  - 今のページが属するプロジェクトを一意に決めるための制約

### 保存

- `chrome.storage.sync` に、プロジェクトごとに 1 項目（キー例: `project:<id>`）で保存し、プロジェクトの並び順は別の 1 項目で持つ
  - 1 項目あたり約 8KB の上限に、プロジェクト全体をまとめた 1 項目では当たりうるため分ける
- 同期がオフの環境では、その PC の中だけに保存される（動作は同じ）
- 別の Chrome での変更は `chrome.storage.onChanged` で受けて、開いているポップアップに反映する
- 複数の端末で同時に編集すると、同じ `origin` が 2 つのプロジェクトに入る、並び順の項目とプロジェクトの項目が食い違う、といった状態が起こりうる。読み込み時に次の規則で黙って 1 つに寄せる（設計者の判断）
  - 同じ `origin` が複数のプロジェクトにあるときは、並び順で先のプロジェクトに残し、後のプロジェクトからは外す
  - 並び順に無いプロジェクトは末尾に足し、存在しないプロジェクトを指す並び順は捨てる

### 切り替え

- ポップアップを開くと、今のタブの URL の `origin` と一致する行き先を探し、そのプロジェクトの行き先一覧を表示する。今いる行き先には印を付ける
- 行き先をクリックすると、`行き先の origin ＋ 今の pathname ＋ search ＋ hash` の URL に今のタブを書き換える
- ⌘クリック（Windows/Linux では Ctrl クリック）と中クリックでは、今のタブの右隣に新しいタブで開く
- `http(s)://` 以外のページ（`chrome://`、`file://`、Chrome Web Store など）では、使えない旨だけを表示する

```
┌──────────────────────────────┐
│ my-service                 ⚙ │
│ ● 本番        example.com      │
│   本番アドミン  admin.example.com │
│   STG1       stg1.example.com  │
│   STG2       stg2.example.com  │
│   ローカル     localhost:3000   │
└──────────────────────────────┘
```

### 登録

登録は「今いるページから足していく」方式のみ。

- 今のページがどのプロジェクトにも属していないとき、ポップアップには次の 2 つを出す
  - 「このページで新しいプロジェクトを作る」: プロジェクト名を 1 つ入力するだけで作成し、今のページの `origin` を最初の行き先にする。プロジェクト名の初期値は今のホスト名
  - 「既存のプロジェクトに追加」: プロジェクトを選んで今のページの `origin` を追加する
- 行き先のラベルの初期値は、ホスト（ポート付きならポートも）をそのまま入れる。あとから管理ページで「STG1」のように書き換えられる

```
未登録のページで開いたとき
┌──────────────────────────────┐
│ stg3.example.com           ⚙ │
│  [＋新しいプロジェクトを作る]       │
│  [＋既存に追加: my-service ▾]   │
└──────────────────────────────┘
```

### 管理ページ

ポップアップは「切り替え」と「今のページの登録」だけに絞り、編集は管理ページ（options ページ）で行う。

- ポップアップの右上に歯車アイコンを置き、押すと管理ページを開く（`chrome.runtime.openOptionsPage`）
- 管理ページには登録済みの全プロジェクトを並べ、どのページを開いているかに関係なく次の操作ができる
  - 行き先のラベルの変更、並べ替え、削除
  - プロジェクト名の変更、プロジェクトの並べ替え、プロジェクトの削除
- プロジェクトの追加（名前だけで作成し、行き先は後から足す）、行き先の追加（スキームとホストを入力する）と、登録済みの行き先のスキーム・ホストの変更もできる。ほかで登録済みの origin にはできない
- ポップアップには今のページが属するプロジェクトだけを出す。ほかのプロジェクトへの切り替えはできない

### UI の品質

- ポップアップの幅は固定し、長いラベルやドメインは省略表示（末尾を「…」）にして、全体はツールチップで見られるようにする。どんな長さでもはみ出さない
- キーボードだけで操作できる（上下キーで移動、Enter で切り替え）

### 多言語対応

- `_locales/en` と `_locales/ja` を用意し、既定は英語
- ストアの掲載文も英語と日本語で用意する

### 信頼性

- コードを public リポジトリで公開する
- 外部への通信をしない、権限は `activeTab` と `storage` のみ、ということを README とストアの掲載文に明記する
- ストア提出に必要なプライバシーに関する開示では、データは利用者の Chrome（と Chrome の同期）にのみ保存し、収集しないと記載する

### ストア公開の範囲

実装の作業に含めるのは次まで（設計者の判断）。

- ストア提出用 zip の作成（WXT のコマンド）
- 掲載文（英語・日本語）と、各権限が必要な理由の説明文
- プライバシーポリシーをリポジトリ内の Markdown として用意し、その GitHub 上の URL をストアに登録できる状態にする。タブの URL から取った `origin` を `chrome.storage.sync` に保存するため、開示で求められる可能性がある

開発者アカウントの登録、スクリーンショットの撮影、実際の提出と審査対応はユーザーが行う。リリースの自動化（GitHub Actions など）は今回は含めない。

### テスト

- Vitest で、URL の組み立て（パス・クエリ・ハッシュの引き継ぎ、ポートやスキームの違い）、`origin` の正規化、今のページが属するプロジェクトの判定、保存処理を中心に書く
- `chrome.*` API は WXT が用意するテスト用の偽実装を使う

## 作る人に任せること

- 画面の細かなデザイン（配色、余白、アイコン）。上の「UI の品質」を満たす範囲で決めてよい
- 並べ替えの操作方法（ドラッグか上下ボタンか）
- 削除時の確認の出し方
- ポップアップを開くキーボードショートカットの初期値の有無
- ID の採番方法、保存する項目の具体的なキー名
- ディレクトリ構成
